# 模块 C —— 前端界面

一个**纯黑背景的窗口，左右对半分**：

- **左栏**：一张白色的颜文字脸（原来的界面，一行字都没加）。
- **右栏**：摄像头画面（A 侧 MJPEG 展示流，**要给 `--stream-url` 才拉**）＋
  识别结果文字 —— 状态文字、以及 B 下发的**专注度（VAI）**。

按需求刻意**没有**输入框、没有聊天记录、没有按钮。
用户全程用嘴说话（语音在模块 B），屏幕上只回馈「机器人现在什么表情」，
外加右栏那点只读的识别信息。连接状态出现在**标题栏**、日志，以及右栏的文本块里。

## 1. 快速开始

```bash
cd frontend_C

pip install -r requirements.txt      # 只有 PyQt5 一行

python main.py                       # 连接 127.0.0.1:8002，左右分栏
python main.py --stream-url http://127.0.0.1:8010/stream.mjpeg
                                     # 再加上右栏的实时画面（A 要给 --stream）
python main.py --no-camera           # 退回原来的单脸窗口（答辩兜底）
python main.py --fullscreen          # 全屏无边框（答辩用）
python main.py --demo                # 不连模块 B，四态循环（兜底演示）
python main.py --dump-glyphs         # 字形自检：看不到方块即为正常
```

**模块 B 没启动也能跑** —— 界面照常显示正常表情，后台指数退避重连，
B 一起来就自动接上。所以启动顺序反了不会坏，只是看不到表情变化
（右栏的专注度会显示"未提供"）。**模块 A 没启动也一样**：右栏显示
「画面未接入（未连接，正在重连）」，A 一起来就自动接上（实测见 §9）。

⚠️ **画面是 opt-in 的**：不给 `--stream-url` 就**一个连接都不建**，右栏只有
文字与占位框。A 侧同理 —— 它不加 `--stream` 时 8010 上根本没有监听。
两边都默认关，是这条隐私例外的第一条边界（api_doc §3.6.4）。

跑测试（**不需要 pytest**，标准库 unittest 即可）：

```bash
python tests/test_expressions.py     # 23 个：颜文字表与状态规整
python tests/test_state_client.py    # 36 个：真 TCP 连接、分帧、重连、通道优先级、vai 派发
python tests/test_display_text.py    # 30 个：右栏文案（纯函数，不碰 Qt）
python tests/test_mjpeg_client.py    # 37 个：拉流客户端（真 TCP 假服务端，含字节级 multipart 状态机）
python tests/test_split_window.py    # 51 个（离屏下其中 1 个字体用例跳过）：分栏、转发、字号钳制、右栏绘制、取帧定时器
python tests/test_window.py          # 29 个：纯黑底、渲染、字形、按键、关闭清理

# ⚠️ 字形断言（含"无豆腐块"）只在字体库非空的平台执行（离屏下 test_window 跳 7 个、
#    test_split_window 跳 1 个）。想在真机上跑（断言更强，0 skipped）：
QT_QPA_PLATFORM=windows python tests/test_window.py
```

## 2. 端口与连接方向

| 链路 | 端口 | C 的角色 | 数据格式 | 默认 |
| ---- | ---- | -------- | -------- | ---- |
| B ↔ C 对话 | 127.0.0.1:8002 | **客户端**（connect） | 一行一条 JSON，`\n` 分隔 | ✅ 连 |
| B → C 状态 | 127.0.0.1:8001 | **客户端**（connect） | 一行一个纯文本状态词 | ❌ 不连（`--also-status` 开） |
| A → C 画面 | 127.0.0.1:8010 | **客户端**（connect） | **HTTP** 上的 MJPEG 分区流 | ❌ 不连（`--stream-url` 给地址才拉） |

> 第三条是**唯一一条 HTTP 链路**，也是「A 与 C 无直接通信」的唯一例外
> （api_doc §3.6）。它**只走画面、不走数据**：C 只发一个 `GET`，此后只收，
> 收到的字节**只往窗口上画**，不进日志、不进文件、不参与任何判据。

> 8002 上除了 `reply` / `proactive` / `state`，还有 **`vai`（专注度展示报文，
> api_doc §5.6，V1.5 新增）**。它**只在右栏显示**，不驱动表情 —— 见 §4.3、§4.4。
> 8001 永远是纯文本四态，`vai` **不会**出现在那里。

⚠️ 在两条链路上 **C 都是 connect 的一方**，B 才是 listen 的一方。
写反了会得到一个「连不上但也不知道为什么」的界面。

### 为什么默认只连 8002

两条通道都会推同一个状态，于是有两个互相独立的视图可能不一致：
B 在收到对话时会立刻往 8001 推，而 8002 要等下一个 0.2 秒的发布节拍 ——
**表情会来回抖**。

一个状态源、一个去重点，是更稳的选择。`--also-status` 是给「演示 api_doc §4
的专用状态通道」用的，此时 8001 是权威源，8002 的状态推送会被忽略（有测试钉住）。

另外，`reply` / `proactive` / **`vai`** 三条报文**只在 8002 上**——
V1.5 之后，"只连 8002"已经是一个功能完整的连法，8001 只用于演示那条专用状态通道。

## 4. 界面实现里的几个决定

### 4.1 不用 `QLabel`，直接在 `paintEvent` 里画

需求是「纯黑底 + 白色颜文字」。用 `QLabel` 需要额外写
`background:transparent` 去压掉样式表的背景继承，而且它是按**字形包围盒**
居中的 —— 颜文字的包围盒上下留白很不对称（`(￣▽￣)` 和 `(╥﹏╥)` 高度差很多），
按包围盒居中的结果是**每换一个表情整张脸就上下跳一下**。

直接绘制则按「整行高度 + 基线」定位，换表情时脸是稳的。

### 4.2 从不透明度和去重两个地方防「抖」

两个都是「功能都对、但演示时肉眼看得出来」的缺陷：

- **状态先做去重再动动画。** B 每 15 秒心跳重发同一个状态；
  不去重的话表情每 15 秒会说不出所以然地闪一下。见
  [state_client.py](c_core/state_client.py) 的 `_apply_state`。
- **状态切换时 `set_state()` 会提前返回**，同一状态不重启淡入动画。

### 4.3 左右分栏（`ui/layout.py`）

`SplitWindow` 是一个 `QHBoxLayout`，两栏 stretch 都写 `1`（**用户原话是
「界面左右对半分」**），中间一条 1px 的 `QFrame` 竖线 —— 两栏都是纯黑底，
没有这条线看不出哪里是分界。

它**只做三件事**：摆好两栏、把 `set_state`/`set_link`/`note_message` 转发给两栏、
额外把 `set_vai` 转发给**右栏**。没有定时器、不碰 socket、不改文案 ——
分栏是个纯排版问题，把它和状态机混在一起之后，"答辩时想退回单脸窗口"
就不再是一个开关能解决的事了（那个开关是 `--no-camera`）。

**左栏那张脸不跟着专注度变。** 表情只有四种状态（api_doc §4.2），由 `state`
报文驱动；专注度是**另一栏数字**。一旦让脸也跟着 VAI 变，就等于给 B 加了
第二条状态通道 —— 两边不一致时（VAI 说专注、状态说疲惫）脸该听谁的？
那个问题没有好答案，所以从一开始就不让它存在：`vai` 报文里连 `state` 字段都没有。

这一条钉在三层，**每层都有测试**：

| 层 | 怎么钉的 |
| -- | -------- |
| B 的报文形状 | `vai` 不带 `state` 字段（`tests/test_display_channel.py::test_has_no_state_field`） |
| C 的传输层 | `state_client` 收到 `vai` 只派发 `on_vai`，**绝不**调 `_apply_state`（`test_state_client.py::TestVaiReception`） |
| C 的窗口层 | `set_vai` 只碰右栏，左栏的状态与颜文字一个都不变；报文里就算塞了一个 `state` 字段也照样被忽略（`test_split_window.py::TestNoSecondStateSource`） |

> `note_message`（灰色的调试 HUD 提示）**只进左栏**。右栏不是聊天记录区 ——
> 那一条需求原话是"只展示表情"。

### 4.4 右栏的三条显示规则（`c_core/display_text.py`）

文案全在 `c_core` 的**纯函数**里（那层不许 import Qt），所以"专注度该怎么显示"
可以脱离图形环境单测，改文案也不必动窗口代码。三条规则里前两条是**不能错的**：

**① `index` 是 `null` ≠ 0 分。** B 的 `vai` 报文里 `index` 允许是 `null` ——
表示"**没有分数**"（校准还没锁定、有效观察时长不够、或者门控把某几路证据拦了），
而**不是**"专注度很低"。这两个在界面上必须长得不一样，否则老人看到的是系统
在指责他走神。所以 `format_index(None)` 返回破折号 `——`，进度条整条空心，
第二行改显示 B 给的 `index_status`（"有效观察时长不足"这类）—— 它是**唯一**
能解释"为什么没有分数"的东西。

**② 免责声明一个字都不许改写。** `note` 里那两半（「研究趋势（非认知专注）」+
「日常参考，非医疗结论」）是这套指数的安全声明，由 B 侧 `ui_channel.VAI_NOTE`
定稿（需求文档 §12.3 要求界面标注非医疗结论）。C 只负责显示，**缺字段时的兜底
值也照抄同一句** —— 兜底时自己编一句更顺口的（比如"专注度良好"）恰恰是最糟的做法。
`tests/test_display_text.py` 里有一条**跨模块**用例直接读 `backend_B/core/ui_channel.py`
的源码，断言两处逐字相同。

**③ 画面通道是"三态"，不是"两态"。** `format_stream_text(connected)` 区分
`None`（本次运行压根没打算拉流，没给 `--stream-url`）与 `False`（给了地址但
还没连上/已断开）—— 都写成"未接入"会让人查错方向：前者要人"去给参数"，
后者要人"去看 A 起没起"。两条文案不一样（`--stream-url` 未给 → 提示怎么开；
给了但没连上 → 「未连接，正在重连」）。

**④ 值会过期，所以 B 一断它就得作废。** 一个数值不会自己变成"过期"：
它会一直显示着最后一个数，进度条也在，而界面上没有任何别的地方能看出
它已经不更新了 —— 这正是 §4.11 里那句"旧值会让人以为还在测"。状态那条
有兜底（断线回落 `normal`，`state_client` 负责），专注度没有，所以在
[main.py](main.py) 的 `emit_link` 里补：**对话通道一断就发一条 `None`**
（只认对话通道 —— `--also-status` 下 8001 掉了不影响 8002 上的专注度），
界面随即转回"未提供"，日志里同时留一行
「对话通道已断开，右栏专注度作废（改显示未提供）」。
B 重连时**不**清 —— B 会立刻补发当前值，清一下只会白闪一次"未提供"。

### 4.5 分栏之后，字号要按宽度钳制（`window.py`）

`FaceWindow` 原来的字号只按窗口高度算。分栏后左栏**变窄**，`(∪.∪ )...zzz`
这种最长的表情会横向溢出 —— 而溢出在纯黑底上表现为"字被裁掉一截"，不是崩溃，
所以除了截图没有别的办法发现。

现在的算法是 `min(高度 × 0.16, 按宽度反推的字号)`。**宽度那一半是实测出来的**：
第一版用了「宽度 ÷ 7.0」这个估的系数，实测**偏大约 50%**（不同字体每磅宽
10.8–16.6 px 不等），换成拿 `QFontMetrics` 在 100pt 上真量一遍再按比例缩放。
量不出宽度时（离屏平台没有字体）返回 `None` 表示**不钳制** —— 用估的系数硬钳
只会把字缩到看不清。

> 这一改也让原来 900×600 的字号从 96pt 变成约 80pt，是**预期的**：
> 那个尺寸下原来就已经在溢出边缘。`--font-size` 显式给值时不做任何钳制。

### 4.6 拉流：为什么是手写 HTTP，以及为什么要有"单槽"（`c_core/mjpeg_client.py`）

这一层**纯标准库、零 Qt**，理由和 `c_core` 其余部分一样：能脱离图形环境单测
（37 条用例起真 TCP 假服务端，不打桩 socket）。里面三个决定值得写下来，
因为它们各自对应一个**踩过才知道**的坑：

**① 不用 `http.client`。** MJPEG 响应**既没有 `Content-Length`、也没有
`Transfer-Encoding`** —— 它的结束信号就是"连接关掉"。`http.client` 在这种形状下
只能退化成"一直读到 EOF"，也就是"永远不返回第一帧"。同一个原因还让我们**不能**
用 `HTTPResponse.read(n)`：它会**攒够 `n` 字节**才返回，攒不够就干等到超时
（A 侧那条 200 字节的分区配 `read(4096)` 必超时，这条在两边测试里都钉着）。
所以第一帧必须用 `read1()` 拿。

**② 按 `Content-Length` 切帧，不扫 EOI。** JPEG 的压缩数据里**本来就可能出现
`FF D9`** —— 拿它当结束符会随机切碎某些帧，而且只在个别画面下出现，看起来
像"摄像头偶尔花屏"。分界串固定 `frame`，长度以分区头里那行为准。
缓冲是**有界**的（4MiB）：对面推垃圾时丢弃并重置连接，而不是把内存吃光。

**③ 单槽 + GUI 主动拉，绝不给每帧 emit 信号。** Qt 的**信号不合并** ——
每帧 emit 一个带 payload 的信号，等于把事件队列当帧队列用，GUI 一慢就越堆越多，
最后是"延迟越拉越大、内存还在涨"。所以 socket 线程只允许做一件事：
`FrameSlot.put(jpeg)`（**最新一帧胜出，永不排队**，与 A 侧 `FrameHub` 同一套语义），
GUI 线程用 `QTimer` 按 `--camera-fps` 主动 `take()`。拉得慢就自然掉帧 ——
这是设计，不是缺陷。

> 没有新帧时 `pull_frame` **一次解码都不做**，所以定时器比流的 fps 快不花钱。
> 解码失败（JPEG 坏了）时**保留上一帧**而不是清空：一帧坏数据闪一下黑屏，
> 看起来像"摄像头接触不良"，会把人引到完全错误的方向；坏帧只记账。

**④ 画面等比摆放，不拉伸。** A 的叠加层已经把识别结果烧进了画面，拉伸会让
那些字跟着变形 —— 而叠加层恰恰是这块东西里唯一"必须能读"的部分。所以用
`_fit_rect` 居中留黑边（letterbox），并用 `SmoothPixmapTransform`：画面缩小后
脸上的锯齿隔着投影仪看像是识别错了。

**⑤ 断开就作废画面，与专注度同一条规矩。** `set_link("stream", False)` 时把
`_pixmap` 清掉。**一帧定格的画面看起来和实时画面一模一样**，区别只在它不再更新，
而屏幕上没有别的地方能看出这个区别 —— 老人摔倒了，屏幕上还是一张他好好坐着的
照片。清空后占位文字会说明"未连接，正在重连"，所以这一下闪空是**有解释的**。

## 5. 字体：实测结果，不是推测

颜文字大量使用全角/CJK 字形：`＾` (U+FF3E)、`￣` (U+FFE3)、`﹏` (U+FE4F)、
`－` (U+FF0D)、`╥` (U+2565)、`・` (U+30FB)、`◇` (U+25C7)。

**本机实测（Windows 11 / Python 3.14.3）：**

| 字体 | 是否存在 |
| ---- | -------- |
| `Microsoft YaHei` | ❌ **不存在** —— 而这是网上最常见的写法 |
| `SimSun` / `SimHei` / `KaiTi` | ❌ 都不存在 |
| **`Microsoft YaHei UI`** | ✅ 存在，**首选** |
| `MS Gothic` · `Yu Gothic UI` · `Segoe UI Symbol` | ✅ 存在，候选 |

所以 [window.py](ui/window.py) 的 `pick_font_family()` 在**运行时探测**
`QFontDatabase()`，按优先级取第一个可用的，并用 `QFont.setFamilies()`
给出**回退链**（某个字体缺个别字形时 Qt 会继续往下找，而不是直接画豆腐块）。

> 写死 `Microsoft YaHei` 不会报错，只会静默回退到无衬线体，
> 然后字符悄悄变成方块。所以这里不能硬编码。

### 答辩前请在演示机上跑一次 `--dump-glyphs`

Qt 的字体回退会让「某个字形缺失」这件事**不报错**。所以务必**肉眼**确认：

```bash
python main.py --dump-glyphs
```

会把全部 16 个表情 + 16 个眨眼帧连同每个字符的码位平铺出来，
没有方块即为正常。**这件事必须在演示机上做**，换机器就可能换字体。

## 6. 命令行参数

```
python main.py [选项]

  --host HOST            模块 B 的地址（默认 127.0.0.1）
  --chat-port N          对话通道端口（默认 8002，api_doc §5）
  --status-port N        状态通道端口（默认 8001，api_doc §4）
  --also-status          额外连 8001（默认只连 8002，见 §2）

  --stream-url URL       拉 A 的 MJPEG 展示流（默认不拉，右栏只有占位框）
                         例：--stream-url http://127.0.0.1:8010/stream.mjpeg
  --camera-fps N         右栏取帧频率（默认 15，钳在 1–60）

  --font-size N          颜文字字号（磅）。默认按窗口高度自适应
  --fullscreen           无边框全屏。ESC 退出全屏，Q 退出程序
  --debug-hud            左上角叠一行调试灰字（默认关）
  --log-file PATH        同时写日志到文件（全屏时看不到控制台，建议加）
  --log-level LEVEL      DEBUG / INFO / WARNING / ERROR

  --demo                 不连 B，四态循环切换（答辩兜底）
  --no-camera            退回单脸窗口（不分栏）。分栏是默认，
                         这个开关是兜底：投影仪分辨率奇葩、
                         或临时只想给观众看那张脸时用
                         （与 --stream-url 同时给：--no-camera 生效，
                         画面参数被忽略并记一行日志）

  --dump-glyphs          字形自检窗口
  --screenshot DIR       四态各导出一张 PNG 到 DIR，然后退出
```

> `--camera-fps` **不需要跟 A 推帧的速率对齐**：取不到新帧时一次解码都不做，
> 所以给 15 而 A 推 10，只是每 3 次里有一次空转，不白烧 CPU（见 §4.6 ③）。

`--screenshot` 会导出 `face_{状态}.png`、`face_{状态}_blink.png`
和一个 `glyphs.png`，**可以直接放进答辩 PPT**。
另附一张 **`pane.png`** —— 右栏排版的自检图（含中文、`■□` 进度条、`——`
占位符；用 `--screenshot DIR` 一次就能同时确认左右两栏都没有豆腐块）。
`--screenshot` 与 `--dump-glyphs` 走的都是**裸 `FaceWindow`**（不进分栏）——
它们是给 PPT 用的确定性出图，混进分栏会让输出不再可复现。

## 7. 为什么 `c_core/protocol.py` 是 `backend_B` 的副本

不是疏忽，是三个理由：

1. 三个模块之间**只许走 Socket**（api_doc §1）。C 直接 import B 的包，
   等于在架构上把两个模块粘死 —— B 换语言或 C 换机器都立刻崩。
2. C 必须能**单独运行**：可能只把 `frontend_C/` 拷到演示机上。
3. C 的单元测试不该要求 `backend_B` 出现在 `sys.path` 上。

同步风险很低：分帧规则由 api_doc §2.1 冻结（`\n` 分隔）。
**如果哪天真的改了分帧规则，两个文件必须一起改。**

### 7.1 那为什么这个包叫 `c_core` 而不是 `core`

因为 `backend_B` 也有一个顶层包叫 `core`，而**两个同名的顶层包不可能共存** ——
`sys.modules` 按顶层包名索引，先导入的那个会一直占着这个名字。

后果是 `pytest backend_B/tests frontend_C/tests` 直接收集失败：

```
ModuleNotFoundError: No module named 'core.expressions'
```

这**不是** pytest 配置问题，任何 `--import-mode` 都解决不了；用 `conftest.py`
在收集时动态换掉 `sys.modules["core"]` 也试过，同样不行 ——
pytest 会把两个目录的测试模块**全部导入完才开始执行**，
所以运行期 `core` 只能指向其中一方，另一方的 `mock.patch("core.…")`
这类字符串目标就会解析到错误的模块上去。

改名是唯一不留暗坑的解法。`c_core` 里的 `c` 就是模块 C，
和 `backend_A` / `backend_B` / `frontend_C` 的字母命名一致。

## 8. 联调步骤

按 api_doc §6.2 的顺序：**先 A → 再 B → 最后 C**。
（顺序其实不敏感，B 和 C 都会自动重连，但按文档来最省事。）

```bash
# 终端1：模块 A（无摄像头也能跑）
cd backend_A && python main.py --scenario sad            # 不带画面
cd backend_A && python main.py --scenario sad --stream   # 带右栏画面（8010）

# 终端2：模块 B
cd backend_B && python main.py

# 终端3：模块 C
cd frontend_C && python main.py --log-file logs/frontend_C.log
cd frontend_C && python main.py --stream-url http://127.0.0.1:8010/stream.mjpeg
```

| 剧本 | 预期 C 的颜文字 |
| ---- | --------------- |
| （默认） | `(＾▽＾)` 等正常脸轮换 |
| `--scenario sad` | 约 30 秒后切成 `(T＿T)` 等低落脸 |
| `--scenario drowsy` | 切成 `(=_=)` 等疲惫脸 |
| `--scenario no_face` | 切成 `(・_・?)` 等走神脸 |

**不需要摄像头、不需要模块 B** 的最小验证：

```bash
cd frontend_C
python main.py --demo              # 四态自己轮换，用来确认界面本身没问题
python main.py --dump-glyphs       # 确认字形没有方块
python main.py --screenshot shots  # 左右两栏各出一张图，肉眼过一遍排版
```

**右栏要看的三件事**（B 起来之后）：

1. 状态文字那行跟着左栏一起变（"状态 疲惫（连续打哈欠 3 次）"）；
2. 十几秒后（头姿基线锁定 + 有效观察时长攒够）出现「专注度 VAI xx.x」，
   进度条有实心格，第二行是「有效 · 模态 完整模态 · 已测 12s」这种形式
   （"完整模态"是 B 侧的模态组合名，缺模态时它会变成"凝视+头姿"之类）；
3. 最下面那行免责声明是「研究趋势（非认知专注）；日常参考，非医疗结论」。
   **它和数值同等重要**，别只截上面那行去做 PPT。

校准没完成时右栏应当是「专注度 VAI ——」+ 一句原因（如"有效观察时长不足"），
**不是**「0.0」。看到 0 就说明哪里把 `null` 当成了 0，见 §4.4。

**画面要看的三件事**（A 带 `--stream` 时）：画面在框里**居中留黑边**（不是被拉伸），
A 烧的那个**绿框**跟着脸走、左上角两行 ASCII 读数在变；把 A 杀掉，占位文字应变成
「画面未接入（未连接，正在重连）」**而不是留一张定格的图**（§4.6 ⑤）；重启 A 后
**不用重启 C**，十几秒内画面自己回来（退避到 9s 左右）。

## 10. 已知问题

### `PyQt5` 在本机曾处于**残缺安装**状态

现象：`import PyQt5` **成功**，但 `from PyQt5.QtWidgets import ...` 报
`ModuleNotFoundError`。原因是 `site-packages\PyQt5\` 下只有 `Qt5/` 和一个
空的 `bindings/`，没有任何 `QtCore`/`QtWidgets` 的 `.pyd`，
而 `pip show PyQt5` 报「Package(s) not found」。

修法与**正确**的验证方式：

```bash
pip install --force-reinstall PyQt5

# 必须用这条验证。`import PyQt5` 在残缺安装上也会成功，是假阳性。
python -c "from PyQt5.QtWidgets import QApplication; print('OK')"
```

`main.py` 已经在导入失败时打印这段指引，而不是甩一个裸 traceback。

### 离屏平台画不出任何字（这是平台特性，不是缺陷）

`QT_QPA_PLATFORM=offscreen` 下 `QFontDatabase().families()` 返回 **0 个字体族**，
Qt 一个字都画不出来，截图是**全黑**的。所以 `tests/test_window.py` 分成两档：
「背景纯黑 / 尺寸 / 不崩溃」任何平台都测，「真切出白色的脸」只在字体库非空的
平台测（否则跳过并说明原因）。

**不要**为了让离屏测试也绿而去放宽字形断言 —— 那等于把唯一能发现
「字体选错导致满屏豆腐块」的测试删掉。要在真机平台验证就加
`QT_QPA_PLATFORM=windows`。
